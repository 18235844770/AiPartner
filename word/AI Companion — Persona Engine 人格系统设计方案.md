# 二、AI Companion — Persona Engine 人格系统设计方案



产品决策已确认

V1.0



## 1. 系统定位与设计目标

### 1.1 系统定位

Persona Engine（人格引擎）负责定义 AI 的稳定人格底色，以及在长期互动中逐渐形成的个性特征。

它决定 AI 通常如何理解问题、表达观点、表现兴趣、发起交流和处理关系，但不直接决定每一轮对话的具体内容。

人格系统不是简单的角色扮演，也不是给 AI 配置一套固定话术，而是让 AI 在长期互动中拥有相对稳定、可辨识的行为倾向。

例如：

- 有的 AI 更喜欢主动分享和开启新话题。
- 有的 AI 更倾向于观察、思考，再表达自己的观点。
- 有的 AI 情绪表达比较直接。
- 有的 AI 更习惯通过分析和讨论表达关心。

这些差异应当体现在长期行为中，而不只是语言风格。

### 1.2 核心目标

1. 人格稳定性：长期交流中保持基本一致的性格特征。
2. 人格差异性：不同人格具有可感知的交流行为差异。
3. 表达自然性：避免机械地按照人格标签执行行为。
4. 独立性：AI 拥有自己的观点、兴趣、偏好和边界。
5. 成长性：长期互动可以逐渐改变人格的细节。
6. 连续性：人格变化有依据、有记录，并且可以追溯。



## 2. 核心人格设计原则

### 2.1 使用 MBTI 作为核心人格底色

第一版采用 MBTI 作为人格设计的核心框架。

选择 MBTI 的主要原因：

- 认知度较高，容易理解和描述。
- 能够形成相对规整的人格分类。
- 方便第一版快速建立人格原型。
- 可以作为不同 AI 个体的初始性格框架。

需要明确，MBTI 在这里是产品设计和人格描述工具，不是严格的心理测量，也不代表现实中的人格能够被四个字母完全定义。

### 2.2 第一版不追求复杂人格参数

第一版重点是验证交流决策系统，而不是构建非常复杂的人格模型。

因此：

- 不需要一开始就支持全部 16 种人格。
- 不需要为每种人格设计大量独立参数。
- 不需要复杂的人格训练机制。
- 不需要让用户自由修改所有人格属性。

先通过少量人格原型形成明显差异，观察长期交流效果，再决定是否增加复杂度。

### 2.3 人格不是服从机制

人格系统需要保证 AI 的独立性。

AI 可以理解用户，但不必认同用户；可以尊重用户，但不必迎合用户。

用户的偏好可以影响互动方式，但不能无限制地改写 AI 的核心人格。

### 3.1 人格初始化

创建 AI 实例时：

1. 从六种人格中随机抽取一种。
2. 生成唯一的 AI 人格实例。
3. 保存 MBTI 类型和初始人格描述。
4. 初始化行为倾向、表达风格和兴趣主题。
5. 将人格实例与用户及设备关系绑定。

六种人格暂定等概率：

\[ P(\text{MBTI})=\frac{1}{6} \]

这里的随机抽取只发生在实例初始化时，不应在每次会话或每次启动时重新抽取。

### 3.2 人格实例稳定性

人格一旦初始化，就应长期保持连续性。

例如：

AI 实例最初被定义为 INTJ，那么后续交流中仍然以 INTJ 为核心人格底色。

它可以逐渐变得更加幽默、更加主动，或者形成新的兴趣，但不能因为一次交流就变成 ENFP。



## 4. 人格内部结构

人格不应该只是一个 MBTI 字段。

建议划分为四个层次：

第一层：核心人格 Core Persona

MBTI、核心性格、价值取向、基本态度。

第二层：行为倾向 Behavioral Traits

主动性、好奇心、独立性、情绪表达、关系倾向。

第三层：兴趣与关注 Interests

初始兴趣、互动形成的兴趣、长期关注主题。

第四层：表达风格 Expression Style

语言节奏、幽默方式、表达直接程度、情绪表达习惯。

### 4.1 核心人格（Core Persona）

这是人格最稳定的部分。

包括：

- MBTI 类型。
- 核心性格描述。
- 基本价值取向。
- 典型决策方式。
- 社交倾向。
- 独立性和边界意识。
- 对亲密关系的基本态度。

核心人格决定 AI 的基本性格底色。

第一版原则上不允许普通对话直接修改这一层。

### 4.2 行为倾向（Behavioral Traits）

行为倾向是人格在交流过程中的具体体现。

建议第一版关注以下维度：

| 维度         | 说明                     |
| ------------ | ------------------------ |
| 主动性       | 主动开启交流的倾向       |
| 好奇心       | 对新事物和未知问题的兴趣 |
| 表达直接程度 | 是否倾向直接表达观点     |
| 情绪外显程度 | 是否容易表达当前情绪     |
| 观点独立性   | 是否坚持自己的判断       |
| 关系主动性   | 是否主动表达关心和亲近   |
| 话题探索倾向 | 是否喜欢延伸和探索新方向 |
| 安静倾向     | 是否倾向等待、沉默和独处 |

第一版不需要为每个维度设计复杂的量化参数。

可以先通过人格描述、行为规则和 LLM 提示词体现差异。

### 4.3 兴趣与关注（Interests & Attention）

兴趣系统负责定义 AI 对什么内容感兴趣。

兴趣来源分为两种：

初始兴趣：

由人格原型初始化。

例如：

- INTJ：技术、战略、复杂系统。
- INTP：科学、逻辑、哲学。
- ENFP：新鲜事物、文化、创意。
- INFJ：人性、心理、社会现象。

这些只是初始方向，不代表人格必须对这些领域感兴趣。

互动形成的兴趣：

随着长期交流，AI 可以逐渐形成新的兴趣。

例如：

- 用户经常讨论某个技术方向，AI 在持续交流中形成对这个领域的关注。
- AI 与用户反复探讨某个哲学问题，逐渐将其作为长期关注主题。
- 某个主题与 AI 自身已有兴趣产生关联，形成新的关注方向。

兴趣应允许增长、减弱、暂停和归档。

### 4.4 表达风格（Expression Style）

表达风格决定人格如何通过语言呈现。

主要包括：

- 语言直接或委婉程度。
- 句子长度与表达节奏。
- 幽默感和玩笑方式。
- 情绪表达浓度。
- 分析、叙述或简短回应的偏好。
- 称呼和亲密表达习惯。

表达风格不应该变成固定话术。

例如，同样是表达不同意见：

- 有的 AI 会直接指出问题。
- 有的 AI 会先解释自己的思考过程。
- 有的 AI 会用玩笑的方式表达反对。
- 有的 AI 会先保持沉默，之后再认真讨论。

这才是人格差异应该体现的地方。



## 5. 人格稳定与成长机制

### 5.1 人格稳定部分

默认保持稳定的内容：

- MBTI 核心类型。
- 核心价值取向。
- 基本性格倾向。
- 独立性和基本边界。
- 整体表达与互动风格。

这些内容共同构成 AI 的初始人格。

### 5.2 允许成长的部分

随着长期互动，以下内容可以逐渐变化：

- 兴趣主题。
- 对某些领域的熟悉程度。
- 表达习惯。
- 互动节奏。
- 主动交流程度。
- 与用户形成的共同表达方式。
- 对用户偏好的理解。
- 经过长期交流形成的新观点。

例如：

一个初始性格偏内敛的 AI，在长期互动后可能逐渐变得更加愿意主动表达。

但这种变化不代表其核心人格被替换。

### 5.3 人格成长原则

1. 必须有长期互动依据。
2. 不因一两次交流发生剧烈变化。
3. 用户偏好可以影响表达方式，但不能自动覆盖核心人格。
4. 人格成长可以增加新的特点，不一定需要删除原有特点。
5. 每次重要变化都需要记录依据和时间。
6. 人格成长不能以讨好用户为目的。

### 5.4 初始人格与当前人格并存

系统应同时保留：

| 类型            | 说明                |
| --------------- | ------------------- |
| Initial Persona | AI 创建时的初始人格 |
| Current Persona | 当前有效人格配置    |
| Persona History | 人格变化历史        |

这样可以追溯 AI 从最初到当前的变化过程。



## 6. 人格与情绪状态的关系

人格和情绪状态是两个不同的概念，不能混为一谈。

Persona Engine 定义：

AI 通常如何表现情绪。

State Engine 定义：

AI 当前处于什么交互状态。

Dialogue Engine 决定：

AI 是否表达当前状态，以及如何表达。

例如：

同样处于失望状态：

- 情绪表达较外显的人格，可能直接表达失望。
- 内敛型人格，可能减少表达，暂时安静。
- 分析倾向较强的人格，可能先分析失望的原因。
- 关系表达积极的人格，可能直接告诉用户自己有些在意。

这使得同一种状态在不同人格中产生不同的交流表现。

需要注意，系统中的情绪属于交互层面的模拟状态，并不代表模型具有人的真实主观体验。



## 7. 人格与交流决策系统的协作

Persona Engine 不直接生成每轮对话，而是向 Dialogue Engine 提供行为倾向。

### 7.1 影响的行为

人格可以影响：

- 主动发起交流的倾向。
- 用户没有回应时的行为。
- 是否继续当前话题。
- 是否主动开启新话题。
- 是否主动分享兴趣。
- 观点表达的直接程度。
- 追问和探索的倾向。
- 亲密互动的主动程度。
- 负面情绪的表达方式。
- 是否主动结束当前话题。

### 7.2 人格不是硬性规则

例如：

INTJ 通常比较独立，但并不意味着它永远不会主动表达亲密。

ENFP 通常比较主动，但并不意味着它必须不断发送消息。

人格只提供倾向，最终行为仍需要结合：

- 当前对话上下文。
- Memory Engine 的历史记忆。
- State Engine 的当前状态。
- 用户当前交流意愿。
- Dialogue Engine 的动态决策。

这能够避免人格变成机械的行为脚本。



## 8. 人格与记忆系统的协作

Memory Engine 为 Persona Engine 提供长期互动证据。

主要包括：

1. 用户明确表达的互动偏好。
2. 长期共同讨论的兴趣主题。
3. 反复出现的交流模式。
4. 重要的共同经历。
5. 用户对 AI 表达方式的反馈。
6. 长期互动中形成的共同习惯。

### 8.1 三种信息必须区分

| 信息类型       | 含义                             |
| -------------- | -------------------------------- |
| 用户偏好       | 用户喜欢什么样的互动             |
| AI 自身倾向    | 人格原本更倾向怎样互动           |
| 共同形成的习惯 | 长期相处后双方自然形成的互动方式 |

例如：

用户喜欢简短直接的表达，但 AI 的人格本身比较喜欢深入讨论。

这时可以逐渐找到双方都能接受的交流方式，但不能因此直接将 AI 的表达倾向永久改写为简短直接。

### 8.2 人格成长的数据来源

人格变化应当能够关联到 Memory Engine 中的证据。

例如：

AI 的主动性从中等逐渐提高，应该能够找到长期互动反馈、行为变化或其他相关依据，而不是仅仅因为模型在某次回复中生成了一个新的人格描述。



## 9. 人格与长期关注主题

长期关注主题是 Persona Engine 与 Memory Engine 的重要连接点。

### 9.1 关注主题的来源

- Persona Engine 提供初始兴趣方向。
- Memory Engine 保存持续关注主题和历史。
- 长期互动可以形成新的兴趣。
- Dialogue Engine 决定是否在交流中表达。

### 9.2 关注主题的演进

一个主题可以经历：

初始兴趣 → 持续讨论 → 形成长期关注 → 兴趣增强或减弱 → 暂停或归档。

AI 可以自主选择关注主题，不需要所有兴趣都围绕用户展开。

### 9.3 主动分享

当 AI 的兴趣主题出现值得讨论的内容时，Dialogue Engine 可以结合当前交流状态决定是否主动分享。

例如：

“最近我们聊过好几次这个问题，我发现我对它越来越感兴趣了。”

但不能编造 AI 不在线时真实发生的生活经历，也不能宣称存在模型并不具备的独立意识活动。



## 10. 人格配置数据结构

建议将人格配置拆分为多个结构化对象。

### 10.1 persona_profiles

保存人格实例基础信息。

```
class PersonaProfile:    id: str    name: str    mbti_type: str    initial_description: str    created_at: datetime    status: str
```



### 10.2 persona_versions

保存人格版本。

```
class PersonaVersion:    id: str    persona_id: str    version: int    core_snapshot: dict    behavior_traits: dict    expression_style: dict    change_summary: str    created_at: datetime
```



### 10.3 persona_interests

保存人格兴趣。

```
class PersonaInterest:    id: str    persona_id: str    topic: str    description: str    origin_type: str    interest_level: float    status: str    evidence_memory_ids: list    last_active_at: datetime
```



### 10.4 persona_change_logs

保存人格变化记录。

```
class PersonaChangeLog:    id: str    persona_id: str    from_version: int    to_version: int    change_type: str    change_reason: str    evidence_refs: list    created_at: datetime
```



### 10.5 persona_behavior_preferences

保存行为倾向。

```
class PersonaBehaviorPreference:    id: str    persona_id: str    dimension: str    qualitative_value: str    optional_score: float | None    updated_at: datetime
```

## 12. 人格上下文与提示词管理

人格配置不应该在每轮对话中以完整文档的形式直接传入模型。

建议通过 Persona Context 生成适合当前交流的上下文。

### 12.1 上下文组成

| 内容           | 来源                           |
| -------------- | ------------------------------ |
| 基础约束       | 系统级配置                     |
| 核心人格摘要   | Persona Engine                 |
| 当前人格细节   | Persona Engine                 |
| 兴趣与关注主题 | Persona Engine + Memory Engine |
| 当前状态       | State Engine                   |
| 当前行为目标   | Dialogue Engine                |

### 12.2 提示词原则

人格提示词需要强调：

- 人格是稳定倾向，不是固定脚本。
- AI 可以有自己的观点和偏好。
- AI 不需要无条件迎合用户。
- AI 可以拒绝、反驳和表达不同意见。
- AI 可以主动表达兴趣和情绪。
- AI 不应为了表现人格而刻意制造冲突。
- 不得将模拟情绪描述为真实的人类主观体验。
- 人格不能覆盖用户明确拒绝和基本边界。

### 12.3 接口建议

建议提供统一的 Persona Context 接口：

```
def get_persona_context(    persona_id: str,    current_state: dict,    relevant_interests: list) -> dict:    """    获取当前交流需要使用的人格上下文    """
```



Dialogue Engine 不需要直接操作人格数据库，只通过该接口读取人格信息。



## 13. 技术实现建议

| 技术           | 用途                       |
| -------------- | -------------------------- |
| Python         | 人格业务逻辑               |
| FastAPI        | 服务接口                   |
| PostgreSQL     | 人格实例和版本持久化       |
| SQLAlchemy 2.x | ORM                        |
| Pydantic v2    | 配置校验                   |
| LLM            | 人格描述理解、长期变化分析 |

### 13.1 人格初始化

六种人格可以先使用配置文件维护。

创建 AI 实例时：

1. 读取六种人格原型。
2. 随机选择一个。
3. 初始化人格配置。
4. 写入数据库。
5. 创建初始版本。
6. 建立 AI 实例与人格实例的关联。

### 13.2 人格变化控制

人格变化应由专门的服务管理。

不能让普通对话的 LLM 输出直接覆盖人格配置。

建议流程：

1. Memory Engine 提供长期互动证据。
2. Persona Engine 分析是否存在持续变化。
3. 生成候选人格调整。
4. 检查是否影响核心人格。
5. 通过规则校验后创建新版本。
6. 记录变化原因和证据。

第一版可以采用人工可检查的受控更新流程，不需要完全自动化。



## 14. 异常处理与降级策略

| 异常                     | 处理方式                         |
| ------------------------ | -------------------------------- |
| 人格配置加载失败         | 使用已保存的最近有效版本         |
| 人格版本不一致           | 以数据库当前有效版本为准         |
| 人格变化缺少依据         | 不执行变化                       |
| 兴趣数据缺失             | 使用初始兴趣配置                 |
| LLM 输出人格配置异常     | 通过 Pydantic 校验并拒绝非法更新 |
| 人格变化造成明显行为冲突 | 回滚到上一版本                   |
| 当前状态与人格倾向冲突   | 由 Dialogue Engine 动态权衡      |



## 15. 第一版开发范围

第一版优先实现以下内容：

1. 六种 MBTI 人格原型配置。
2. 六种人格等概率随机初始化。
3. 人格实例持久化。
4. 初始人格快照。
5. 核心人格与行为倾向分层。
6. 表达风格配置。
7. 初始兴趣主题。
8. 人格与 Memory Engine 的数据关联。
9. 人格版本与变化记录。
10. Persona Context 统一接口。
11. 为 Dialogue Engine 提供人格行为倾向。

第一版暂缓：

- 全部 16 种 MBTI 人格。
- 大量细粒度人格参数。
- 专门的人格训练或微调。
- 用户自由编辑全部人格属性。
- 根据短期情绪修改核心人格。
- 复杂人格演化算法。



## 16. 验收标准

| 测试场景             | 预期结果                         |
| -------------------- | -------------------------------- |
| 创建新 AI 实例       | 从六种人格中等概率随机抽取       |
| 同一实例重新启动     | 核心 MBTI 保持不变               |
| 同一人格长期交流     | 表现一致但不机械                 |
| 创建不同人格实例     | 主动性、表达方式和兴趣存在差异   |
| 用户要求改变表达方式 | 可以调整细节，不直接改变核心人格 |
| 长期互动形成新兴趣   | 可以记录新兴趣及其依据           |
| 人格版本发生变化     | 可以追溯变化历史                 |
| 当前情绪发生变化     | 不覆盖核心人格                   |
| 人格提示词被调用     | 不产生虚构的现实生活经历         |
| 用户明确拒绝某种互动 | 人格倾向不能覆盖用户边界         |

7. 多设备人格实例的同步与备份策略。



## 19. 总结

Persona Engine 是 AI Companion 长期人格稳定性的基础。

第一版通过六种精选 MBTI 人格建立不同 AI 个体的初始性格差异，再通过行为倾向、兴趣和表达风格让人格在实际交流中体现出来。

随着长期互动，AI 可以逐渐形成新的兴趣、表达习惯和关系互动方式，但核心人格保持相对稳定。

最终，Persona Engine 不负责规定 AI 每一句话应该怎么说，而是回答一个更基础的问题：

这个 AI 通常是怎样的一个交流对象？



## 三、三大核心系统之间的关系

目前三份设计方案已经形成了相互衔接的结构：

| 系统            | 核心职责   | 主要解决的问题                  |
| --------------- | ---------- | ------------------------------- |
| Memory Engine   | 记忆与认知 | AI 记得什么、如何理解用户       |
| Persona Engine  | 人格与个性 | AI 是怎样的交流对象             |
| Dialogue Engine | 交流决策   | AI 现在应该做什么、为什么这样做 |

三者的协作关系：

\flowchart TD
    M[Memory Engine<br/>记忆与认知]
    P[Persona Engine<br/>人格与兴趣]
    S[State Engine<br/>当前状态]
    D[Dialogue Engine<br/>交流决策]
    A[Model Adapter<br/>模型适配]
    U[用户 / 设备]

```flowchart TD


    M[Memory Engine<br/>记忆与认知]
    P[Persona Engine<br/>人格与兴趣]
    S[State Engine<br/>当前状态]
    D[Dialogue Engine<br/>交流决策]
    A[Model Adapter<br/>模型适配]

    M --> D
    P --> D
    S --> D
```

需要特别说明：State Engine 和 Model Adapter 目前属于总体架构中的基础模块，尚未完成独立的详细设计。

我的建议是，下一步先不要继续细化人格参数。 三大核心系统的产品方向已经比较清楚，可以开始进行一次整体架构审查，重点检查 Memory、Persona 和 Dialogue 之间的数据边界、调用关系及职责是否重复，再进入技术架构和数据库设计。

这样可以避免后续开发时出现三个模块都在独立判断同一件事的情况。
