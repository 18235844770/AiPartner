# AI 伴侣移动端前端实现标准

**文档版本：** V1.0  
**适用范围：** AI 伴侣移动端 UI 第一版  
**文档性质：** 前端开发统一规范  
**设计基准：** AI 伴侣移动端高保真设计稿 V1.0

---

# 1. 项目目标与基本原则

## 1.1 项目目标

本规范用于指导 AI 伴侣移动端前端开发，确保最终实现与高保真设计稿保持一致，同时建立可维护、可扩展的前端工程结构。

第一版需要完成以下页面：

1. 登录页面
2. 首页
3. 聊天页面
4. 设置页面

前端不仅需要实现静态 UI，还需要支持页面交互、角色动态展示、消息交互和后续语音能力扩展。

## 1.2 核心实现原则

所有前端开发必须遵守以下原则：

- 设计稿优先：以正式高保真设计稿为视觉依据，不得随意改变布局和视觉风格。
- 组件化：公共 UI、页面 UI 和业务逻辑分离。
- 数据驱动：页面展示由状态和数据控制，不通过直接操作 DOM 实现业务逻辑。
- 动画独立：角色动画与页面业务逻辑解耦。
- 移动端优先：首先保证移动端尺寸下的布局与交互。
- 可扩展：为后续语音、通知、角色个性化等能力预留接口。
- 不做过度设计：不得擅自增加设计稿中不存在的卡片、统计面板和功能入口。

# 2. 技术规范

## 2.1 技术栈

第一版前端采用以下技术：

| 技术 | 规范 |
|---|---|
| Vue | Vue 3 |
| 语言 | TypeScript |
| 构建工具 | Vite |
| 状态管理 | Pinia |
| 路由 | Vue Router |
| 样式 | CSS / SCSS |
| 动画 | Rive，必要时配合 CSS / SVG |
| 网络请求 | Axios 或统一 Fetch 封装 |
| 实时通信 | SSE |
| 图标 | SVG 图标资源 |

具体依赖版本以项目现有 package.json 为准，不得未经评估随意升级核心依赖。

## 2.2 开发规范

- 使用 Vue 3 Composition API。
- 优先使用 `<script setup lang="ts">`。
- 禁止在业务代码中滥用 `any`。
- 公共类型统一定义。
- 组件 Props 和 Emits 必须有明确类型。
- 异步操作必须处理加载状态和异常状态。
- 禁止在 Vue 组件中直接编写大量网络请求逻辑。
- 禁止将复杂业务逻辑全部堆积在页面组件中。

# 4. UI 设计系统规范

## 4.1 视觉基准

正式视觉风格：

**Pastel Companion：2D 扁平插画 + 马卡龙配色 + 轻量装饰。**

核心视觉特征：

- 紫色为品牌主色。
- 白色和灰白色为主要页面背景。
- 粉色、黄色、薄荷绿、浅蓝作为辅助色。
- 使用圆润、柔和的 UI 组件。
- 角色采用 2D 扁平云朵形数字生命体。
- 装饰元素主要用于首页和登录页。
- 聊天页以阅读体验为优先。
- 设置页保持简洁。

禁止擅自修改为 3D 风格、深色科技风、复杂渐变风或其他与设计稿不一致的视觉方向。

## 4.3 字体规范

| 场景 | 字号建议 |
|---|---:|
| 页面标题 | 24–28px |
| 模块标题 | 17–19px |
| 正文 | 15–16px |
| 辅助文字 | 12–13px |
| 按钮 | 15–16px |

优先使用系统无衬线字体。

中文字体需要兼容 iOS 和 Android 系统。

## 4.4 组件规范

### 按钮

- 主按钮使用品牌紫色。
- 次按钮使用白色或浅紫色背景。
- 按钮圆角保持统一。
- 必须包含正常、按下、禁用和加载状态。
- 点击区域应满足移动端触控需求。

### 输入框

- 背景以浅灰白为主。
- 圆角保持统一。
- 输入状态和错误状态必须清晰。
- 支持键盘类型、密码显示控制和表单校验。

### 卡片

- 白色或低饱和辅助色背景。
- 圆角 16–20px。
- 轻阴影。
- 不允许无意义地增加卡片层级。

# 5. 页面实现规范

## 5.1 登录页面

### 页面职责

完成用户身份认证和应用入口。

### 页面结构

1. 语言选择。
2. 角色展示区域。
3. 产品名称及标语。
4. 邮箱输入框。
5. 密码输入框。
6. 忘记密码。
7. 登录按钮。
8. 邮箱验证码登录。
9. 注册入口。
10. 服务条款和隐私政策。

### 功能要求

- 邮箱格式校验。
- 密码输入和显示控制。
- 登录请求加载状态。
- 登录失败提示。
- 忘记密码流程。
- 邮箱验证码登录。
- 注册页面跳转。
- 登录成功后进入首页。

### 视觉要求

- 保留角色作为主视觉。
- 不得将角色图片作为整页背景。
- 表单区域需要独立实现。
- 装饰图形不得遮挡输入框和按钮。

## 5.2 首页

### 页面职责

展示陪伴者的存在状态，并提供主要功能入口。

### 页面结构

1. 日期。
2. 当前时间。
3. 设置入口。
4. 中央动态角色。
5. 角色名称。
6. 状态文字或自然表达气泡。
7. 底部导航。

### 功能要求

- 时间动态更新。
- 角色状态动态展示。
- 角色动画响应状态变化。
- 支持进入聊天页面。
- 支持进入语音功能入口。
- 支持进入其他功能入口。

### 视觉要求

- 角色为页面视觉中心。
- 保留设计稿中的装饰元素。
- 不增加统计、记忆卡片和最近会话面板。
- 角色容器尺寸固定，动画不得影响页面布局。

## 5.3 聊天页面

### 页面职责

承载用户与 AI 伴侣的核心交流。

### 页面结构

1. 顶部返回。
2. 更多操作。
3. 角色展示区域。
4. 角色名称。
5. 当前状态。
6. 消息列表。
7. 消息输入区域。

### 消息规范

- 用户消息靠右。
- AI 消息靠左。
- 用户消息采用浅紫色背景。
- AI 消息采用浅色背景。
- 不为每条消息显示角色头像。
- 同一角色连续消息自动分组。
- 消息最大宽度建议约为容器宽度的 82%。
- 字体建议 15–16px。
- 时间信息只在必要时展示。

### 即时聊天机制

AI 一轮回复允许包含多条独立消息。

要求：

- 前端不得简单地将长文本按字符数量强制切割。
- 消息顺序必须保持一致。
- 支持 AI 消息逐条到达。
- 支持用户在 AI 连续输出过程中插话。
- 新输入到达时，取消或重新评估尚未发送的后续内容。
- 网络中断时能够正确处理未完成的消息。
- 不允许前端自行伪造 AI 回复。

消息到达间隔由后端 Dialogue Engine 控制，前端负责按事件顺序展示，不人为制造不必要的等待。

### 角色展示约束

这是聊天页的重要约束：

**所有角色动态反馈只在顶部头像区域体现。**

禁止：

- 在消息气泡中插入角色表情。
- 在消息列表中展示角色动画。
- 为每条 AI 消息重复展示角色头像。
- 通过额外状态卡片干扰阅读。

### 输入区域

第一版支持：

- 文本输入。
- 附件入口。
- 表情入口。
- 发送按钮。

语音交互暂时不纳入本阶段实现范围，但应避免架构上阻碍后续扩展。

## 5.4 设置页面

### 页面职责

负责应用配置、账号管理、隐私和帮助入口。

### 页面结构

- 陪伴者：角色资料、外观偏好。
- 聊天体验：聊天设置、通知设置。
- 应用：外观设置、数据与隐私。
- 其他：关于、帮助与支持。

### 产品约束

以下内容不得设计成可手动修改的配置项：

- AI 记忆。
- AI 情绪状态。
- AI 关系状态。
- AI 人格核心特征。

这些内容由系统内部机制维护。

角色名称和有限的外观偏好可以作为用户配置项。

用户个人数据的导出、删除和隐私权利需要独立设计，不得与 AI 自主记忆机制混为一谈。

# 6. 动态角色 Avatar Engine

## 6.1 设计目标

角色是产品最重要的视觉资产之一。

必须将角色动画设计为独立模块，不能将动画逻辑直接写在首页或聊天页面中。

## 6.2 角色视觉规范

- 2D 扁平插画。
- 不规则软团子轮廓。
- 极简眼睛和嘴巴。
- 可选腮红。
- 不设置传统人物身体和手脚。
- 不使用 3D 模型。
- 不将角色实现为普通静态 Emoji。

不同人格允许具有不同轮廓和配色，但必须遵循统一的基础视觉语言。

## 6.3 技术方案

推荐：

- Rive：主体动画和状态机。
- SVG：五官、主体矢量资源和辅助图形。
- CSS：简单页面装饰动画。
- TypeScript：Avatar Controller。

## 6.4 动画状态

第一版至少支持：

| 状态 | 行为 |
|---|---|
| Idle | 呼吸、轻微浮动 |
| Blink | 眨眼 |
| Happy | 开心表情、轻微弹跳 |
| Shy | 脸颊变化、轻微收缩 |
| Angry | 表情收紧、短促动作 |
| Sad | 下沉、低频动作 |
| Thinking | 视线偏移、轻微倾斜 |
| Listening | 注视用户、偶尔眨眼 |
| Speaking | 嘴部动态变化 |

## 6.5 动画实现约束

- 待机动画应当轻微、自然。
- 不同动作之间需要平滑过渡。
- 不允许多个冲突动作同时触发。
- 动画不得改变页面布局。
- 动画状态不能直接由 LLM 文本任意控制。
- Emotion Engine 提供情绪状态，Avatar Controller 负责映射动画。
- 必须提供资源加载失败时的静态角色回退方案。
- 页面不可见时应合理降低动画开销。

角色动画组件应能够被首页、聊天页和未来语音页面复用。

# 7. 页面状态管理

## 7.1 全局状态

建议使用 Pinia 管理：

- 用户认证状态。
- 当前陪伴者信息。
- 当前页面相关会话信息。
- 全局应用设置。
- 网络连接状态。

## 7.2 页面局部状态

页面内部状态尽量由组件自身维护，不要为了方便将所有数据塞进全局 Store。

## 7.3 状态规范

异步页面必须明确区分：

- Loading：加载中。
- Success：成功。
- Empty：空状态。
- Error：异常。
- Offline：离线。

不能只实现正常数据展示，而忽略异常状态。

# 8. 网络请求和实时通信

## 8.1 API 请求

统一封装 API Client。

要求：

- 统一请求基础配置。
- 统一认证信息处理。
- 统一错误处理。
- 统一超时处理。
- 统一响应数据类型。
- 不允许每个组件独立创建 Axios 实例。

## 8.2 SSE

聊天实时消息使用 SSE。

前端需要处理：

- 连接建立。
- 消息接收。
- 消息顺序。
- 消息事件类型。
- 连接中断。
- 连接恢复。
- 请求取消。
- 消息结束状态。
- 服务端异常事件。

SSE 事件协议必须以实际后端定义为准，不允许前端自行猜测事件名称和字段。

## 8.3 数据边界

前端不负责：

- AI 人格决策。
- AI 记忆提取。
- AI 长期记忆管理。
- 情绪状态计算。
- 关系状态计算。
- 多消息生成策略。

这些职责属于后端业务和 AI 认知系统。

前端只负责接收、展示、交互和必要的客户端状态管理。

# 9. 移动端适配规范

## 9.1 基本要求

优先适配移动端常见屏幕尺寸。

建议以 375px 宽度作为基础视觉校验尺寸，并验证 390px、414px 等常见视口。

不得只在单一尺寸下完成开发。

## 9.2 布局规范

- 页面宽度自适应。
- 内容区域避免固定绝对定位。
- 使用 Flex 和 Grid 完成主要布局。
- 角色展示区域可以使用受控定位。
- 输入区域需要适配安全区域。
- 底部导航应考虑 iOS Home Indicator。
- 不得出现横向滚动条。

## 9.3 安全区域

正确处理：

- iOS 顶部状态栏。
- iOS 底部安全区域。
- Android 状态栏。
- 软键盘弹出。
- 输入框聚焦后的页面滚动。

## 9.4 触控要求

- 重要操作具备足够触控区域。
- 不依赖 Hover 交互。
- 避免过小的图标点击区域。
- 页面切换和按钮操作必须有清晰反馈。

# 10. 性能和异常处理

## 10.1 性能要求

- 页面按需加载。
- 大型动画资源按需加载。
- 图片使用合理尺寸。
- 避免不必要的重复渲染。
- 避免频繁触发昂贵的 DOM 操作。
- 长聊天列表应考虑虚拟滚动或分段加载。
- 不在主线程执行耗时计算。

## 10.2 异常处理

至少覆盖：

- 网络请求失败。
- 登录认证失败。
- SSE 连接中断。
- 图片加载失败。
- 动画资源加载失败。
- 用户重复点击。
- 页面切换过程中请求未完成。
- 用户主动取消请求。

异常提示应简洁、明确，避免暴露内部堆栈和服务端敏感信息。

# 11. 代码质量规范

## 11.1 组件设计

组件应遵循单一职责原则。

页面组件负责组合和组织，不应承担全部业务逻辑。

公共组件不得依赖具体页面的内部状态。

## 11.2 TypeScript

- 所有核心业务对象必须定义类型。
- API 响应必须定义接口。
- 事件参数必须明确类型。
- 尽量使用联合类型表达状态。
- 避免不安全类型断言。

## 11.3 代码风格

- 变量名使用有意义的英文。
- 组件名采用 PascalCase。
- 函数名采用 camelCase。
- 常量使用明确的命名。
- 禁止无意义的重复代码。
- 禁止保留大量废弃代码。
- 禁止通过增加 CSS 覆盖层掩盖结构性问题。

## 11.4 禁止事项

- 不得为了快速实现将整个页面做成一张背景图片。
- 不得把所有组件写在一个 Vue 文件中。
- 不得绕过统一 API 服务层。
- 不得将后端业务规则复制到前端自行判断。
- 不得使用随机动画模拟真实情绪状态。
- 不得随意改变已经确认的视觉规范。
- 不得擅自增加产品功能。
- 不得以静态假数据冒充已接通的真实接口。

# 12. 开发实施顺序

建议按以下顺序推进：

## 阶段一：工程基础

1. 检查现有项目结构。
2. 建立或整理公共目录。
3. 配置 Design Tokens。
4. 建立全局样式。
5. 建立公共按钮、输入框、图标等组件。
6. 配置路由和基础状态管理。

## 阶段二：静态页面实现

依次完成：

1. 登录页面。
2. 首页。
3. 聊天页面。
4. 设置页面。

先保证视觉还原度，再接入复杂业务逻辑。

## 阶段三：角色系统

1. 整理角色素材。
2. 制作 Rive 动画资源。
3. 建立 Avatar Controller。
4. 建立情绪到动画的映射。
5. 接入首页和聊天页。

## 阶段四：业务接入

1. 登录认证。
2. 用户资料。
3. 聊天消息。
4. SSE 实时通信。
5. 设置和隐私接口。

## 阶段五：质量验收

1. 视觉对比。
2. 页面适配。
3. 交互测试。
4. 网络异常测试。
5. 动画性能测试。

# 13. 视觉验收标准

所有页面必须通过视觉验收。

验收基准为正式高保真设计稿。

检查项目：

| 验收项 | 标准 |
|---|---|
| 页面结构 | 与设计稿一致 |
| 页面背景 | 颜色和装饰一致 |
| 角色位置 | 大小、比例和位置一致 |
| 字体 | 字号、字重和颜色一致 |
| 组件 | 圆角、尺寸和间距一致 |
| 图标 | 使用正式素材 |
| 消息气泡 | 位置、颜色和宽度一致 |
| 底部导航 | 图标、布局和选中状态一致 |
| 动画 | 不影响布局和交互 |
| 屏幕适配 | 不出现遮挡和溢出 |

每个页面完成后必须：

1. 在目标视口下运行。
2. 截取实际页面。
3. 与对应高保真设计稿对照。
4. 修正明显差异。
5. 完成验收后再进入下一页面。

不得以“页面能够正常显示”作为视觉验收通过的唯一标准。

# 14. 开发完成定义

一个页面只有同时满足以下条件，才能视为完成：

- 页面结构符合设计稿。
- 视觉样式通过对照。
- 主要交互可以正常使用。
- 加载、空状态和异常状态已处理。
- 组件结构合理。
- TypeScript 类型检查通过。
- 不存在明显控制台错误。
- 移动端适配通过。
- 不存在明显性能问题。

# 15. Cursor 执行规则

Cursor 在执行前端任务时必须遵守：

1. 先检查现有工程，不得直接重建项目。
2. 先阅读本规范，再开始编码。
3. 优先复用现有组件和业务服务。
4. 不得擅自更改已经确定的产品设计。
5. 不得用占位图片替代已有正式素材。
6. 不得虚构后端接口和事件协议。
7. 不确定的功能先确认，不得自行扩大需求。
8. 每次只推进一个明确的开发阶段。
9. 完成后说明修改的文件、实现内容和未完成事项。
10. 遇到架构级问题必须先说明风险，不得通过临时补丁掩盖。
