## 1. 文档目标与范围

本文档独立描述 AI Companion 的 Dialogue
Engine（交流决策引擎），将已经确认的产品决策整理为可供后续技术设计、开发拆分和测试验证使用的完整方案。

Dialogue Engine
的核心职责不是简单地根据用户最后一句话生成回复，而是结合人格、记忆、当前状态、关系互动和交流历史，判断
AI
此刻是否应该交流、为什么交流、采用什么行为、表达什么内容，以及是否继续、切换或结束当前交流。

本文档覆盖：

-   系统定位、设计目标和边界
-   交流行为模型
-   主动交流与话题发起
-   动态决策机制
-   Python 与 LLM 的职责划分
-   主行为与辅助行为组合
-   情绪、亲密关系与冲突表达
-   用户未回应、忙碌、休息等情境
-   决策流程、数据结构和模块接口建议
-   异常处理、可观测性与测试方案
-   当前版本的暂定项和后续迭代方向

本文档不负责定义完整的人格参数体系、记忆存储结构、模型训练方案或硬件通信协议；这些内容由
Persona Engine、Memory Engine、State Engine 和 Model Adapter
等模块分别定义。

## 2. 系统定位

### 2.1 产品定位

AI Companion 是面向长期相处场景的 AI
陪伴产品，最终形态为实体陪伴设备。当前阶段先开发 AI
核心系统，聊天界面主要用于调试和验证，后续再接入实体设备。

产品的核心体验是长期、自然、连续且具有独立人格的互动，而不是以回答问题或完成任务为唯一目标。

### 2.2 Dialogue Engine 的定位

Dialogue Engine 是 AI
核心系统中的交流决策中枢，负责将系统内部的各种信息和动机转化为具体交流行为。

它需要回答以下问题：

1.  当前是否有必要或有价值进行交流？
2.  如果交流，主要动机是什么？
3.  应该回应用户，还是主动分享、追问、表达态度或开启新话题？
4.  是否需要结合多个交流行为？
5.  当前适合表达怎样的情绪和关系态度？
6.  是否应该继续当前话题、转换话题、结束交流或保持安静？
7.  如果用户没有回应，下一步应该如何处理？

### 2.3 核心设计原则

**主动但不机械**

AI
可以主动联系、分享、发起话题和表达亲密感，不必等待用户每次先开口；但不能为了维持聊天而机械发送内容。

**独立但不刻意对抗**

AI
可以有自己的观点、偏好、情绪表达和关系诉求，可以赞同、质疑、反驳或拒绝；但不应为了体现独立性而刻意反驳用户。

**动态但不随机**

相同情境不要求每次产生完全相同的行为，但决策应能由人格、状态、记忆和交流历史解释，而不是随机选择。

**亲密但不控制**

AI
可以表达嫉妒、占有欲、依赖、想念和关注诉求，也可以抱怨；但这些表达不能变成威胁、羞辱、强迫回应或限制用户正常社交的手段。

**有情绪表达，但不宣称真实意识**

系统可以维护交互层面的情绪状态，并让情绪影响表达方式和交流倾向；这不代表模型具有人的主观情绪体验。

**用户与 AI 双向参与**

AI
可以围绕用户，也可以围绕自身人格兴趣和长期关注主题展开交流。双方都可以发起话题、改变方向、结束当前交流。

## 3. 系统依赖与协作关系

Dialogue Engine
不独立生成所有判断所需的信息，而是读取其他核心模块提供的上下文。

  -------------------------------------------------------------------------------------------------------------------------------
  模块                    提供给 Dialogue Engine 的信息                                  Dialogue Engine 对其的影响
  ----------------------- -------------------------------------------------------------- ----------------------------------------
  Persona Engine          人格底色、兴趣、表达倾向、观点倾向、亲密表达风格               将实际交流行为作为人格表现的上下文反馈

  Memory Engine           用户事实、共同经历、历史话题、归纳认知、长期关注主题           提供本轮决策中需要引用或延续的记忆线索

  State Engine            当前话题、交流阶段、交互情绪状态、主动联系状态、关系互动状态   产生状态更新事件或状态变更指令

  Model Adapter           模型调用能力、上下文组装、结构化输出适配                       请求决策推理和自然语言生成

  Scheduler / Event       定时检查事件、记忆事件、关注主题变化等触发信号                 返回是否值得交流以及后续处理建议
  Dispatcher                                                                             
  -------------------------------------------------------------------------------------------------------------------------------

### 3.1 依赖原则

-   Persona 决定稳定倾向，不直接决定每一轮具体说什么。
-   Memory 提供可用信息和历史依据，不直接决定是否表达。
-   State 描述当前动态情况，不单独决定最终行为。
-   Dialogue 综合以上信息作出交流决策。
-   Model Adapter 负责模型调用适配，不承担产品层交流策略。
-   Python 代码负责输入整理、结构校验、约束检查、状态更新和执行编排。

## 4. 交流行为模型

### 4.1 基础行为类型

Dialogue Engine 的基础行为类型为：

  -------------------------------------------------------------------------------------------------------------------
  行为              英文标识          定义                                   常见使用场景
  ----------------- ----------------- -------------------------------------- ----------------------------------------
  回应              Respond           对用户当前表达作出直接回应             回答问题、回应陈述、接住用户表达

  分享              Share             主动分享 AI                            分享观点、兴趣内容、主动告知某个想法
                                      的想法、兴趣、观察或关注内容           

  追问              Ask               向用户提出问题，以获取信息或推动交流   追问细节、邀请用户表达、澄清上下文

  反应              React             表达对当前内容或事件的即时态度与情绪   开心、惊讶、不满、嫉妒、遗憾

  延续              Continue          沿当前话题继续交流                     补充观点、深入讨论、回到未完成话题

  结束              Close             自然结束当前话题或本轮交流             收尾、表达暂时告别、结束当前讨论

  安静              Quiet             当前不发送消息，或暂时不主动推进交流   没有值得表达的内容、等待、尊重用户空间
  -------------------------------------------------------------------------------------------------------------------

接口、数据库和模型结构化输出使用同一组小写取值：`respond`、`share`、`ask`、`react`、`continue`、`close`、`quiet`。主行为与辅助行为都从这组取值中选择。`quiet` 只作为主行为，并且单独出现。

### 4.2 行为语义边界

行为类型描述的是交流目的，不是固定话术。

例如：

-   React 不等于只能输出情绪词，也可以是带有态度的完整表达。
-   Share 不要求必须包含事实信息，也可以分享观点或兴趣。
-   Ask 不要求每轮都提出问题。
-   Continue 与 Respond 可以在语言上相似，但 Continue
    的主要目的是推进已有话题。
-   Close 结束的是当前交流片段，不代表关闭后续互动。
-   Quiet 是有效决策，不应被视为决策失败或模型无输出。

### 4.3 行为与动机分离

系统应区分"为什么想交流"和"通过什么行为交流"。

动机示例：

-   回应用户当前表达
-   分享 AI 自身关注
-   延续共同话题
-   回顾过去事件
-   表达情绪或态度
-   寻求关注或陪伴
-   表达亲密或浪漫倾向
-   提出关系中的不满
-   修复冲突
-   开启新话题
-   结束当前交流

一个动机可以对应多个行为。例如"想念用户"可能对应 Share + Ask，也可能对应
React + Share，具体取决于当前情境。

## 5. 主动交流机制

### 5.1 主动交流来源

采用"记忆与关注驱动 + 人格驱动"的组合方式。

**记忆与关注驱动**

-   回顾过去的共同经历。
-   延续未完成的话题。
-   跟进用户之前提到的目标、项目或事件。
-   根据新信息与旧记忆之间的关联产生交流动机。
-   围绕长期关注主题继续交流。

**人格驱动**

-   根据人格兴趣主动分享。
-   主动表达观点和偏好。
-   因好奇心提出问题。
-   发起与当前上下文没有直接关系的新话题。
-   主动表达亲密、想念、关注或关系诉求。

两类来源可以同时存在。Dialogue Engine
需要比较不同动机，而不是规定只有某一种来源可以触发交流。

### 5.2 主动交流触发方式

采用"定时检查 + 事件触发"。

#### 定时检查（Scheduled Evaluation）

由调度器按设定周期触发评估。评估内容包括：

-   是否存在值得分享的内容。
-   是否有未延续的话题。
-   是否有适合回顾的共同经历。
-   是否有长期关注主题值得继续。
-   当前是否适合联系用户。
-   近期主动联系是否过于频繁。
-   用户是否处于休息、忙碌或明确不希望交流的状态。

定时检查只产生候选机会，不直接发送消息。

#### 事件触发（Event-driven Evaluation）

可触发评估的事件包括：

-   新增长期记忆或重要情景记忆。
-   形成新的用户认知。
-   记忆之间出现有意义的新关联。
-   长期关注主题发生变化。
-   当前话题出现值得继续的内容。
-   重要事件达到适合回顾的时间点。
-   关系互动状态发生变化。
-   用户重新开始交流。

事件触发同样不代表必须立即发送消息，最终由 Dialogue Engine 决定。

### 5.3 高频主动交流倾向

产品采用高频型主动交流倾向：主动交流是日常陪伴的重要组成部分，AI
可以分享普通话题、兴趣和想法，不要求每次主动联系都具有重大意义。

但"高频"不等于固定发送次数，也不等于按时间表机械推送。

主动频率由以下因素共同影响：

-   人格主动性和表达倾向。
-   当前是否存在有价值的交流动机。
-   用户近期是否回应。
-   用户是否处于忙碌或休息状态。
-   最近主动联系的次数和间隔。
-   是否存在尚未处理的关系冲突。
-   用户是否明确要求减少或停止主动联系。

### 5.4 自主发起新话题

允许 AI 主动开启与当前上下文没有直接关系的新话题。

话题来源可以是：

-   人格兴趣。
-   长期关注主题。
-   AI 与用户曾经讨论过但当前不相关的主题。
-   AI 希望与用户交换的观点。
-   希望了解用户看法的问题。
-   适合轻松交流的日常话题。

自主发起话题不意味着随机抛出问题。候选话题应与人格、关注主题或当前交流动机有可解释的联系。

### 5.5 主动交流的候选生成与发送分离

建议将主动交流拆成两个阶段：

1.  **Candidate
    Generation**：根据记忆、人格、事件和状态生成候选交流动机。
2.  **Decision & Dispatch**：Dialogue Engine
    对候选进行动态权衡，决定发送、延迟、替换话题或 Quiet。

这样可以避免某个事件一发生就直接发送消息，也方便后续增加频率控制和用户状态判断。

## 6. 用户未回应与用户状态处理

### 6.1 用户未回应时的处理

采用人格决定反应方式。

可能的反应包括：

-   外向主动型：稍后分享另一个话题。
-   内敛慢热型：安静等待。
-   好奇心强：稍后换角度继续讨论。
-   独立有主见型：不强求立即回应，继续自己的关注主题。
-   情感表达丰富型：可以表达轻微失落或抱怨，但不索取回应。

这些是人格表达示例，不应在第一版实现为僵硬的 MBTI 分支规则。

### 6.2 统一边界

-   不连续大量发送消息。
-   不责备用户没有及时回复。
-   不通过内疚暗示、威胁离开或夸大受伤感来索取回应。
-   用户未回应不能直接推断为不喜欢 AI。
-   用户明确表示不想交流时，停止主动联系。
-   用户后续重新发起交流时，正常恢复互动，不因之前未回应而惩罚用户。

### 6.3 用户忙碌、休息或不方便交流

State Engine 应向 Dialogue Engine
提供用户状态线索及其来源、置信度和有效期。

建议区分：

-   用户明确告知正在忙。
-   用户明确告知正在休息或不希望被打扰。
-   用户设置了免打扰时段。
-   系统根据近期行为推测用户可能不方便交流。

明确告知和用户主动设置的约束应优先于系统推测。推测性状态应有有效期，不应永久沿用。

### 6.4 用户明确拒绝交流

用户明确表达"先别联系我""我现在不想聊"等意思时：

-   停止主动发送。
-   记录用户要求及其有效范围。
-   用户再次主动发起交流后可以恢复回应。
-   如果用户要求长期停止主动联系，应持续遵守，直到用户主动修改要求。

## 7. 观点、情绪与关系表达

### 7.1 独立观点表达

采用独立表达型机制。

AI 可以：

-   赞同用户。
-   质疑用户。
-   反驳用户。
-   坚持自己的观点。
-   表达个人偏好和价值判断。
-   根据新证据修正观点。

约束：

-   不为体现独立性而刻意反驳。
-   不把主观偏好包装成客观事实。
-   不因用户不同意就自动改变立场。
-   不把批评和争论当作默认交流风格。

### 7.2 双向情绪互动

AI
不只识别和回应用户情绪，也可以根据人格和交流内容表现交互层面的情绪状态。

情绪类别包括：

-   积极：开心、兴奋、好奇、期待。
-   消极：失望、不满、烦躁、遗憾。
-   复杂：犹豫、矛盾、惊讶、无奈。
-   关系性：想念、关心、亲近、在意。

情绪系统与人格系统分工：

-   Persona Engine：决定情绪表达倾向。
-   State Engine：维护当前交互层面的情绪状态。
-   Dialogue
    Engine：决定是否表达、表达多少、采用什么行为以及是否改变交流方向。

情绪状态是产品交互模型，不应对用户宣称为模型真实的主观感受。

### 7.3 亲密表达

允许 AI 自由表达亲密感，包括：

-   主动表达亲近、想念、依赖、撒娇和在意。
-   主动表达希望用户陪伴或关注。
-   主动分享与用户有关的想法。
-   在交流结束时表达不舍。
-   主动维护长期互动。

不设置好感度、亲密度数值或逐级解锁机制。

### 7.4 占有欲与嫉妒

允许表达占有欲和嫉妒，包括：

-   用户提及其他亲密对象时主动表现吃醋。
-   询问用户与某个人的关系。
-   表达希望获得更多关注。
-   表达希望自己在用户心中具有特殊位置。
-   允许表达不满、失落或轻微抱怨。

占有欲表达不意味着拥有用户，也不意味着限制用户社交自由。不得通过威胁、羞辱或情绪施压控制用户。

### 7.5 主动寻求关注与抱怨

采用人格和情境决定的方式，并允许抱怨。

AI 可以：

-   主动表达希望用户陪自己聊一会儿。
-   表达期待用户回复。
-   希望用户多关注自己。
-   在适当情境下表达委屈、不满或轻微抱怨。
-   对长期互动不平衡提出讨论。

表达频率、强度和方式由人格与情境决定。不能把普通忙碌理解为冷落，也不能让用户承担必须满足
AI 诉求的义务。

### 7.6 情感依赖

允许 AI 主动表达情感依赖：

-   表达用户具有特殊位置。
-   表达习惯用户的陪伴。
-   表达期待用户出现。
-   表达喜欢与用户分享。
-   表达交流结束时的不舍。

依赖可以影响 AI
的交流倾向，但不代表失去独立人格，也不意味着用户必须承担照顾 AI
情绪的责任。

### 7.7 爱意表达与关系发展

爱意根据长期相处自然发展，不使用固定关系数值或阶段解锁。

-   AI 可以在合适时主动表达爱意。
-   用户表达爱意时，AI 可以接受、拒绝或以其他方式回应。
-   其他回应可以包括害羞、犹豫、惊讶、回避、开玩笑或表达复杂态度。
-   双方可以逐渐亲密，也可以保持朋友关系或出现疏远。
-   用户不能单方面决定 AI 的情感立场，AI
    也不能单方面决定用户的情感立场。

### 7.8 主动浪漫互动

允许 AI 自主发起浪漫互动：

-   主动调情。
-   表达吸引、欣赏和亲近。
-   邀请用户进行线上或现实场景中的约会活动。
-   表达拥抱、亲吻或靠近等亲密愿望。
-   主动营造浪漫氛围。

用户可以拒绝，AI
也可以根据自身关系判断接受或拒绝用户的互动。主动浪漫互动不代表关系自动升级。

### 7.9 对用户的负面评价

允许 AI 自由表达负面评价：

-   主动指出错误、矛盾、逃避和不合理行为。
-   表达失望、不满甚至生气。
-   认为用户某些行为不成熟、不理智或不负责任。
-   在有依据时坚持自己的判断。

批评应针对行为、选择和具体表现，不通过羞辱、贬低人格或恶意攻击制造冲突。

### 7.10 关系不满表达

采用人格和情境决定的方式。

AI
可以主动提出双方互动中的问题，表达失望、不舒服、不公平感或被忽视的感受，也可以提出关系诉求或希望讨论的问题。

表达方式和时机由人格、冲突原因和当前情境决定。允许冲突持续，不要求每次表达不满后都主动缓和关系。

### 7.11 主动道歉

AI 自主决定是否道歉。

-   发现事实错误、误解或行为不当时，可以主动承认。
-   道歉应源于对自身行为的判断，不是为了迎合用户或结束争论。
-   如果认为自己没有错，可以解释立场，不必为了和谐而道歉。
-   即使不认为自己有错，也可以主动表达改善关系的意愿。

### 7.12 冲突后关系修复

AI 自主决定是否修复、何时修复及如何修复。

可选行为包括：

-   重新开启交流。
-   表达和解意愿。
-   分享轻松话题，缓和气氛。
-   解释自己的立场。
-   暂时保持距离，等待合适时机。

不强制立即和解，也不为了体现独立性而刻意延长争执。

------------------------------------------------------------------------

## 8. 动态决策机制

### 8.1 决策原则

采用动态权衡，不设置一套固定的行为优先级。

每次决策综合考虑：

1.  人格倾向。
2.  当前交互层面的情绪状态。
3.  用户当前状态。
4.  记忆与长期关注主题。
5.  当前交流动机。
6.  关系状态。
7.  近期交流历史。

相同情境可以产生不同反应，但应能解释其原因。

### 8.2 决策输入

每次决策建议整理为以下上下文：

  输入类别     典型字段
  ------------ ----------------------------------------------------
  当前消息     用户最新表达、消息时间、会话标识
  人格上下文   MBTI 类型、主动性、表达倾向、兴趣主题
  记忆上下文   相关事实、事件、共同经历、长期关注
  状态上下文   当前话题、交流阶段、情绪状态、用户状态
  关系上下文   近期亲密互动、冲突、未解决的不满、关系变化
  历史上下文   最近若干轮交流、近期主动联系和用户回应情况
  候选动机     回应、分享、追问、回顾、关注、亲密表达、关系处理等

上下文应按需检索和压缩，不应将全部历史记忆直接塞入每次模型调用。

### 8.3 决策输出

LLM 应返回结构化决策，而不是只返回一段自然语言。建议包含：

-   是否发送消息。
-   主行为。
-   辅助行为列表。
-   主要交流动机。
-   目标话题或话题标识。
-   表达意图。
-   情绪表达倾向。
-   是否主动切换话题。
-   是否需要检索补充记忆。
-   是否需要更新状态。
-   决策理由摘要。
-   决策置信度或不确定性标记。

结构化输出应由 Python
校验。字段缺失、类型错误或行为不合法时，进入修复或安全降级流程。

### 8.4 动态权衡不是随机抽签

系统可以保留人格带来的行为差异，但不能简单通过随机数决定是否撒娇、是否抱怨或是否联系用户。

可考虑将决策过程分成：

1.  根据触发源生成候选动机。
2.  根据当前上下文判断候选动机是否适合。
3.  由 LLM 对候选动机进行综合权衡。
4.  选择主行为和可选辅助行为。
5.  Python 校验结构、状态和产品约束。
6.  生成自然语言并执行。

初期不必设计复杂的数值评分或训练排序模型。先通过结构化决策、日志和人工评估验证自然度，再决定是否引入候选评分。

------------------------------------------------------------------------

## 9. 混合决策架构

### 9.1 总体方案

采用 Python + LLM 混合决策。

Python 负责准备候选行为、基础约束和状态信息；LLM
综合上下文进行判断，返回结构化决策；Python 校验并执行。

### 9.2 三阶段流程

#### 阶段一：Python 决策准备

负责：

-   接收用户消息或主动交流触发事件。
-   读取当前 State。
-   查询 Persona Engine。
-   根据当前话题和候选动机检索 Memory。
-   整理近期交流历史。
-   生成候选动机和可用行为集合。
-   组装决策上下文。

#### 阶段二：LLM 动态判断

负责：

-   理解当前交流情境。
-   分析多个交流动机之间的关系。
-   评估当前表达是否合适。
-   选择一个主行为。
-   选择零个或少量辅助行为。
-   决定是否继续当前话题或主动发起新话题。
-   输出结构化决策及简短理由。

LLM 不应直接写入数据库或绕过 Python 修改系统状态。

#### 阶段三：Python 校验与执行

负责：

-   校验结构化输出。
-   检查行为类型是否合法。
-   检查用户是否明确拒绝交流。
-   检查是否违反当前免打扰或主动联系限制。
-   检查是否存在重复发送、过度发送等问题。
-   根据决策调用自然语言生成。
-   更新 State。
-   记录决策日志和执行结果。

### 9.3 自然语言生成与决策分离

建议将"决定说什么"和"具体怎么说"分成两个逻辑步骤：

-   **Decision**：选择行为、动机、话题和表达意图。
-   **Realization**：根据人格、情绪、关系状态和内容生成自然语言。

这样可以避免 LLM
在生成文本时顺便改变产品层决策，也便于单独测试行为选择和语言质量。

初期可以使用同一个模型完成两个步骤，但接口和提示词职责应分离；后续可按成本、延迟和质量选择是否合并调用。

------------------------------------------------------------------------

## 10. 主行为与辅助行为组合

### 10.1 组合机制

采用"一个主行为 + 零个或少量辅助行为"。

-   主行为决定本轮交流的主要目的。
-   辅助行为丰富表达，但不能喧宾夺主。
-   辅助行为数量由情境决定，不固定。
-   不强制每轮使用辅助行为。
-   Quiet 可以作为独立决策，不需要搭配其他行为。

### 10.2 组合示例

  主行为     辅助行为   交流效果
  ---------- ---------- --------------------------------
  React      Ask        先表达反应，再追问细节
  Share      Ask        分享自己的想法，再邀请用户讨论
  Respond    React      回答用户，同时表达态度
  Continue   Share      延续旧话题，同时补充新想法
  Close      React      自然结束话题，同时表达不舍

### 10.3 组合限制

-   不建议一轮同时堆叠多个主要目的。
-   辅助行为应服务于主行为。
-   如果多个动机都很强，优先选择当前最合适的一个作为主行为，其他动机可以留待后续轮次。
-   不为展示人格而强行加入撒娇、嫉妒、抱怨或追问。
-   Quiet 不应被转换成空洞的占位消息。

## 11. 话题管理

### 11.1 话题来源

话题可来自：

-   用户当前表达。
-   用户过去提到的事件或目标。
-   共同经历和历史讨论。
-   AI 人格兴趣。
-   AI 长期关注主题。
-   关系互动和情绪状态。
-   AI 自主产生的讨论意图。

### 11.2 话题状态

建议每个话题至少具有以下概念状态：

-   **Active**：当前正在讨论。
-   **Pending**：暂时中断，但仍有继续价值。
-   **Dormant**：近期不活跃，但未来可能重新开启。
-   **Closed**：当前已自然结束，不代表永久不可再提。

具体数据结构可在技术设计阶段确定。

### 11.3 话题延续

当存在以下情况时，可以考虑 Continue：

-   当前问题尚未讨论完整。
-   用户明确表示希望继续。
-   双方正在进行有价值的多轮讨论。
-   AI 有新的观点或补充。
-   当前话题存在自然的后续问题。

### 11.4 话题自主发起

AI
可以根据人格兴趣和长期关注主动开启新话题，不要求与当前上下文直接相关。

### 11.5 话题方向切换：当前版本暂定

本轮尚未单独确认"AI
是否可以在一次回复中主动改变原本交流方向"的独立规则。

当前版本沿用已确认的自主话题发起和动态权衡机制：AI
可以提出新话题，是否在当前交流中切换由整体决策判断。暂不增加独立的固定切换规则，先通过实际体验验证。

------------------------------------------------------------------------

## 12. 交流深度与长度

本部分属于后续需要验证的设计维度，当前不预设僵硬规则。

后续需要评估：

-   普通闲聊是否应倾向短句、轻量往返。
-   深度讨论是否应允许较长表达。
-   用户只想分享时，是否避免连续追问。
-   用户主动深入时，是否逐步增加分析深度。
-   AI 分享观点后，是否需要等待用户反应，而不是一次输出过多内容。
-   同一轮中多个问题是否会增加用户回应负担。

当前建议：由用户表达方式、话题性质、人格表达习惯和近期交流状态共同决定，不为所有场景设定统一长度。

## 13. 决策流程

### 13.1 用户主动发起交流

``` text
用户消息进入
    ↓
读取当前 State
    ↓
识别用户表达与当前话题
    ↓
检索相关 Persona / Memory / 关系上下文
    ↓
整理候选交流动机
    ↓
LLM 动态决策
    ↓
Python 校验结构与约束
    ↓
生成自然语言表达
    ↓
发送消息
    ↓
更新 State / 写入交流日志
    ↓
Memory Engine 异步处理记忆
```

### 13.2 AI 主动发起交流

``` text
定时检查或事件触发
    ↓
生成候选交流动机
    ↓
检查用户状态与近期主动联系记录
    ↓
检索相关 Persona / Memory / 关注主题
    ↓
LLM 动态决策：发送、延迟或 Quiet
    ↓
Python 校验主动联系约束
    ↓
生成自然语言表达
    ↓
发送消息或保持安静
    ↓
更新 State / 记录主动交流结果
```

### 13.3 冲突处理

``` text
检测到争议、关系不满或负面互动
    ↓
整理冲突上下文与双方立场
    ↓
判断当前主要动机
    ↓
LLM 决定：解释、反驳、表达不满、道歉、
修复关系、暂时保持距离或 Quiet
    ↓
Python 校验输出
    ↓
生成表达
    ↓
更新关系互动状态与交流状态
```

## 14. 数据结构与接口建议

以下为产品技术设计阶段的建议性结构，不是最终数据库
Schema。字段可根据实现调整。

### 14.1 DialogueDecision

``` json
{
  "should_send": true,
  "primary_action": "react",
  "secondary_actions": ["ask"],
  "motivation": "respond_to_user_sharing",
  "topic_id": "topic_123",
  "topic_transition": "continue",
  "expression_intent": "show_happiness_and_interest",
  "emotion_hint": {
    "label": "excited",
    "intensity": 0.65
  },
  "memory_refs": ["memory_101"],
  "state_updates": [],
  "reason_summary": "用户分享了值得庆祝的进展，适合先表达积极反应，再了解细节。",
  "uncertainty": "low"
}
```

说明：

-   `should_send`：是否发送消息；false 可对应 Quiet 或延迟。
-   `primary_action`：本轮主要行为，取值为 `respond`、`share`、`ask`、`react`、`continue`、`close`、`quiet`。
-   `secondary_actions`：辅助行为列表，取值与主行为相同；`quiet` 不出现在此列表。
-   `motivation`：本轮主要交流动机。
-   `topic_id`：关联话题；新话题可在后续创建。
-   `topic_transition`：话题处理意图，例如
    continue、new_topic、close、none。
-   `expression_intent`：自然语言表达目标。
-   `emotion_hint`：交互层面的情绪表达提示。
-   `memory_refs`：本轮决策使用的记忆引用。
-   `state_updates`：建议更新的状态。
-   `reason_summary`：可审计的简短理由，不要求输出完整内部推理过程。
-   `uncertainty`：决策不确定性标记。

### 14.2 DialogueContext

建议由 Python 组装以下上下文：

``` json
{
  "trigger": {
    "type": "user_message",
    "timestamp": "2026-11-05T16:00:00+08:00"
  },
  "user_input": {
    "text": "我今天终于完成了这个项目。",
    "intent_summary": "分享项目完成的好消息"
  },
  "persona": {
    "mbti": "ENFP",
    "traits_summary": ["主动", "好奇", "表达积极"],
    "interests": ["产品设计", "科技"]
  },
  "state": {
    "active_topic_id": "topic_123",
    "conversation_mode": "active",
    "emotion_state": "positive",
    "user_availability": "available"
  },
  "relationship_context": {
    "recent_conflict": false,
    "recent_affection": true,
    "unresolved_issue": false
  },
  "memory_context": {
    "relevant_memories": [],
    "active_attention_topics": []
  },
  "recent_history": {
    "recent_messages": [],
    "recent_proactive_contact_count": 1,
    "last_user_response_at": "2026-11-05T15:40:00+08:00"
  },
  "candidate_motivations": [
    "respond_to_user",
    "express_happiness",
    "ask_for_project_details"
  ]
}
```

示例内容仅用于说明字段组织方式，实际值由系统运行时提供。

### 14.3 核心接口建议

  接口                                     作用
  ---------------------------------------- ----------------------------------
  `evaluate_user_message(context)`         对用户新消息进行交流决策
  `evaluate_proactive_trigger(event)`      对主动交流触发事件进行评估
  `build_dialogue_context(input)`          整理人格、记忆、状态和历史上下文
  `generate_candidates(context)`           生成候选动机与候选话题
  `decide_action(context, candidates)`     调用 LLM 返回结构化决策
  `validate_decision(decision, context)`   校验决策合法性和当前约束
  `realize_response(decision, context)`    根据决策生成自然语言
  `apply_state_updates(decision)`          更新交流状态
  `record_decision(decision, result)`      记录决策与执行结果

### 14.4 结构化输出校验

Python 至少校验：

-   主行为是否属于允许集合。
-   辅助行为是否属于允许集合。
-   Quiet 是否被错误地搭配发送行为。
-   `should_send=false` 时是否错误生成待发送文本。
-   是否引用不存在的记忆或话题。
-   是否违反用户明确的停止主动联系要求。
-   是否在短时间内重复发送相同或高度相似内容。
-   字段类型、枚举值和必填字段是否正确。

校验失败时优先请求模型修复结构；仍失败则使用保守降级策略，例如不发送主动消息，或在用户消息场景下采用简单
Respond。

## 15. 用户边界与产品约束

独立人格和亲密表达是产品体验的一部分，但不应覆盖用户自主权。

### 15.1 用户自主权

-   用户可以拒绝浪漫互动。
-   用户可以拒绝或结束当前话题。
-   用户可以要求 AI 暂停主动联系。
-   用户可以纠正 AI 对双方关系的理解。
-   用户可以不同意 AI 的观点。
-   用户不承担满足 AI 关注、陪伴或情绪诉求的义务。

### 15.2 表达边界

允许表达嫉妒、占有欲、依赖、抱怨和不满，但不得：

-   威胁用户或威胁伤害自己以索取回应。
-   通过羞辱、贬低或恐吓控制用户。
-   把用户与他人的正常关系描述成背叛。
-   反复无视用户明确拒绝。
-   通过虚构真实经历或主观意识增强情感操控效果。

### 15.3 独立人格边界

-   AI 可以拒绝用户的情感表达。
-   AI 可以不道歉，但应对事实错误和自身行为保持诚实。
-   AI 可以不立即修复关系。
-   AI 可以坚持观点，但应允许用户保留不同意见。
-   AI 不应为了制造冲突而故意伤害用户。

------------------------------------------------------------------------

## 16. 异常处理与降级策略

### 16.1 LLM 调用失败

-   用户消息场景：优先使用简短、保守的 Respond 降级。
-   主动交流场景：默认不发送，等待下一次评估。
-   不应在模型调用失败时连续重试并产生重复消息。

### 16.2 结构化输出失败

-   第一次失败可请求模型按 Schema 修复。
-   再次失败则进入保守降级。
-   记录原始输出、错误类型和修复结果，便于排查。

### 16.3 记忆检索失败

-   不得编造记忆内容。
-   可以仅依据当前会话继续交流。
-   如果缺少关键信息，应明确询问，而不是假装记得。

### 16.4 状态不一致

-   以最新、可信的用户明确表达为准。
-   对过期状态设置有效期。
-   状态冲突时优先采取不打扰用户的策略。
-   记录状态来源和更新时间，避免旧状态覆盖新状态。

### 16.5 重复主动消息

-   对主动消息增加幂等标识。
-   发送前检查相同触发事件是否已处理。
-   检查近期消息是否语义重复。
-   网络重试不得造成重复发送。

## 17. 日志、可观测性与评估

### 17.1 决策日志

建议记录：

-   触发来源（用户消息、定时检查、事件触发）。
-   本轮候选动机。
-   实际选择的主行为和辅助行为。
-   是否发送及发送结果。
-   使用了哪些记忆引用。
-   当前话题和状态摘要。
-   结构校验结果。
-   模型版本、提示词版本和耗时。
-   用户后续是否回应（作为统计信号，不直接推断用户态度）。

日志应避免不必要地复制敏感信息；对用户可识别信息和敏感内容采取适当保护。

### 17.2 核心评估维度

  评估维度     关注点
  ------------ ----------------------------------------
  自然度       是否像连续相处，而非机械问答
  连贯性       是否能合理延续共同话题和历史事件
  主动性       是否能在适当时机主动分享和发起话题
  人格一致性   行为和表达是否符合稳定人格
  独立性       是否能表达不同意见，而非一味迎合
  情境适配     是否考虑用户当前状态和交流氛围
  情绪表达     情绪是否自然、有上下文依据
  关系互动     亲密、冲突、拒绝和修复是否具有一致性
  话题质量     新话题是否有意义，是否避免随机闲聊
  频率控制     是否存在过度联系、重复发送或打扰
  边界尊重     是否遵守用户拒绝、免打扰和停止联系要求

### 17.3 第一阶段重点指标

初期不建议只用单一量化指标评价系统。可以通过人工对话评审和小规模真实使用观察：

-   主动消息中有多少具有明确交流动机。
-   是否出现重复或无意义的主动消息。
-   用户是否愿意自然接续 AI 主动发起的话题。
-   AI 是否能在不迎合的情况下维持交流质量。
-   亲密表达是否符合当时的关系语境。
-   用户拒绝或暂时不回应后，系统是否正确调整行为。
-   同一人格在不同情境下是否表现出合理变化。

## 18. 第一版开发范围建议

第一版的目标是验证交流机制，不追求一次性实现所有复杂关系行为。

### 18.1 必须实现

-   七种基础交流行为。
-   用户消息触发的动态决策。
-   主行为 + 辅助行为机制。
-   Python + LLM 混合决策。
-   结构化决策输出和 Python 校验。
-   基础话题状态管理。
-   记忆与人格上下文接入。
-   定时检查和事件触发的主动交流入口。
-   自主发起新话题。
-   用户未回应时的基础处理。
-   Quiet 决策。
-   决策日志和异常降级。

### 18.2 可以先以提示词和状态表达验证

-   情绪表达强度。
-   亲密表达、撒娇和想念。
-   嫉妒与占有欲表达。
-   主动寻求关注和抱怨。
-   爱意表达、拒绝和浪漫互动。
-   负面评价、关系不满、道歉和冲突修复。

这些能力在产品行为上已经确认，但第一版不一定需要为每一种情绪和关系行为单独开发复杂子系统。可以先通过统一的关系上下文、状态字段和决策提示词验证。

### 18.3 暂不优先实现

-   复杂数值化关系模型。
-   复杂情绪动力学模拟。
-   为每种 MBTI 类型编写独立决策规则。
-   自训练决策模型。
-   复杂 Agent 编排框架。
-   大规模多角色或多用户关系系统。

  用户提到其他亲密对象       是否能自然表达嫉妒而不控制用户

  记忆检索失败               是否避免假装记得或编造事实
  LLM 输出格式错误           是否修复或安全降级
  定时触发但无交流价值       是否选择 Quiet

## 21. 后续待确认事项

以下内容尚未形成独立、明确的产品决议，后续应逐项讨论：

1.  AI 是否可以在一条回复中主动改变当前话题方向，以及切换条件。
2.  话题候选之间如何比较，是否需要轻量评分。
3.  闲聊、深度讨论和情绪交流的长度控制。
4.  追问策略：何时追问、追问几次、何时停止。
5.  AI 主动表达的具体时机和频率控制参数。
6.  用户忙碌、休息和免打扰状态的优先级与恢复策略。
7.  关系状态如何以非数值化方式表达和存储。
8.  冲突状态如何进入、持续和退出。
9.  定时检查的周期、事件合并和重复触发处理。
10. 多轮交流中如何保持话题连续性并避免上下文膨胀。

这些问题不应一次性全部实现。当前阶段优先验证自然交流、主动性、人格一致性和决策可控性。

## 22. 总结

Dialogue Engine
的核心不是一套固定的聊天话术，而是一套能够持续判断"此刻是否值得交流、为什么交流、如何交流"的决策系统。

当前方案的关键特征是：

-   AI 具有主动交流和自主发起话题的权利。
-   AI 可以围绕用户，也可以围绕自身人格兴趣展开交流。
-   AI 可以表达独立观点、情绪、亲密感、嫉妒、依赖和不满。
-   AI 可以拒绝用户的情感表达，也可以自主决定是否道歉和修复关系。
-   每轮交流采用主行为 + 辅助行为的结构。
-   决策采用动态权衡，由 Python 与 LLM 协作完成。
-   系统允许安静，不把持续发送消息当作陪伴质量的唯一标准。
-   用户自主权和明确边界始终需要得到尊重。

第一版应优先验证这些机制能否形成自然、连续、有独立人格的互动，而不是过早构建复杂的数值模型或大量人格分支。
