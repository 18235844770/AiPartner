# CosyVoice3 语音逐字顿挫问题专项诊断方案

## 一、任务目标

当前 AI 伴侣项目使用以下语音模型：

- ASR：`iic/SenseVoiceSmall`
- ASR Backend：`sensevoice`
- TTS：`Fun-CosyVoice3-0.5B-2512`
- TTS Backend：`cosyvoice3`
- 推理精度：FP16
- GPU：NVIDIA RTX 3060 Ti

目前存在严重语音播放问题：

**AI 语音几乎每个汉字之间都会出现瞬间断续，听感像机器人逐字念稿，而不是自然连贯的中文语音。**

本次任务只进行诊断和验证，暂时不要直接修改生产代码、替换模型或调整核心架构。

最终需要明确：
1. 问题是否由 CosyVoice3 模型生成导致。
2. 问题是否由文本切分或 TTS 调用方式导致。
3. 问题是否由音频分块、拼接或后处理导致。
4. 问题是否由 WebSocket 传输导致。
5. 问题是否由 Electron 前端播放机制导致。
6. 确定最可能的根因，并提供可复现证据。

## 二、第一阶段：检查现有代码

先阅读项目现有实现，不要立即修改。

重点检查：

### 1. TTS 调用层
- CosyVoice3 是否使用官方推荐的推理接口。
- 是否错误地对每个汉字、词语或短句分别调用模型。
- 是否每次调用都重新初始化推理流程。
- 是否正确传入 `prompt_text` 和 `prompt_speech`。
- 是否正确使用 `stream=True/False`。
- 是否存在文本预处理导致的字符间断。
- 是否将标点符号处理成过长停顿。

### 2. 音频生成层
检查：
- 每个 chunk 的采样率。
- 每个 chunk 的实际时长。
- 每个 chunk 的 PCM 数据长度。
- 每个 chunk 的生成耗时。
- chunk 是否存在首尾静音。
- chunk 拼接时是否存在音频间隙。
- 是否对每个 chunk 单独执行归一化、重采样或编码。
- 是否错误地丢弃了模型返回的部分音频。

### 3. 音频传输层
检查：
- WebSocket 是否逐块发送音频。
- 是否存在队列阻塞。
- 是否存在发送间隔异常。
- 是否存在音频 chunk 顺序错误。
- 是否错误地将文本 chunk 和音频 chunk 一一对应。

### 4. Electron 播放层
检查：
- 是否每个 chunk 单独创建 AudioContext 或 AudioBufferSourceNode。
- 是否每个 chunk 播放完成后才创建下一个播放器。
- 是否存在主线程阻塞。
- 是否存在播放队列调度不及时。
- 是否存在缓冲区不足。
- 是否存在重复启动、提前停止或错误清理 AudioContext。
- 是否正确处理音频播放时间轴。

特别注意：不能采用每个音频块播放完毕后再启动下一个音频块的串行方式。应使用连续音频时间轴进行调度。

## 三、第二阶段：建立四组独立对照实验

使用完全相同的中文测试文本、相同音色参考音频、相同模型权重和推理参数。

统一测试文本：

今天晚上我想和你聊聊最近发生的事情。其实有些想法我已经考虑很久了，只是一直没有找到合适的机会告诉你。

### 实验 A：非流式原始模型输出

目的：确认模型本身生成的音频是否自然。

要求：
1. 直接调用 CosyVoice3 官方非流式推理接口。
2. 一次性传入完整测试文本。
3. 禁止文本切分。
4. 禁止 WebSocket。
5. 禁止 Electron 播放。
6. 保存模型直接输出的原始音频。

输出：
- `A_raw.wav`
- 模型推理日志
- 音频采样率、声道数、位深、总时长
- RTF

判断：
如果原始音频已经存在明显逐字断续，优先检查模型推理参数、文本预处理、参考音频及模型加载方式。

### 实验 B：流式模型输出

目的：确认模型自身流式生成是否正常。

要求：
1. 使用与实验 A 相同的完整文本。
2. 调用官方流式推理接口。
3. 不经过 WebSocket 和 Electron。
4. 在 Python 端收集所有原始音频 chunk。
5. 按正确顺序合并音频。
6. 保存合并后的完整音频。

输出：
- `B_stream_merged.wav`
- 每个 chunk 的生成耗时。
- 每个 chunk 的音频时长。
- 每个 chunk 的采样率。
- 相邻 chunk 的生成间隔。
- chunk 首尾静音统计。

判断：
- A 正常、B 异常：检查流式推理及 chunk 拼接。
- A、B 都异常：继续排查模型调用和输入条件。

注意：不能为了拼接而擅自裁剪音频或增加淡入淡出。先保留原始数据，另行生成分析副本。

### 实验 C：后端生成完整 WAV，前端播放

目的：隔离 WebSocket 流式传输和前端实时播放。

要求：
1. 使用实验 A 生成的 `A_raw.wav`。
2. 通过项目现有音频接口传给 Electron。
3. 前端等待完整文件接收完成。
4. 一次性播放完整 WAV。
5. 不经过逐块播放逻辑。

输出：
- 播放结果。
- 接收完整音频所需时间。
- 文件传输前后大小及校验值。

判断：
如果 A 正常、C 异常，排查音频传输、解码、格式处理及播放器。

### 实验 D：完整流式链路

目的：验证真实产品播放链路。

要求：
1. 使用现有完整链路。
2. 保留流式 TTS。
3. 保留 WebSocket。
4. 保留 Electron 播放。
5. 对每个音频块记录完整时间戳。
6. 记录前端缓冲区长度及播放时间轴。

输出：
- 完整链路日志。
- 播放录音。
- 各层时间戳。
- 缓冲区耗尽次数。
- 播放中断次数。

## 四、第三阶段：增加统一诊断日志

所有时间使用单调时钟，避免系统时间变化影响计算。

每个音频 chunk 必须记录：

```json
{
  "task_id": "test_001",
  "chunk_index": 0,
  "generate_start": 0,
  "generate_end": 0,
  "send_time": 0,
  "receive_time": 0,
  "schedule_time": 0,
  "play_start_time": 0,
  "sample_rate": 24000,
  "channels": 1,
  "audio_duration_ms": 0,
  "audio_bytes": 0
}
```

具体时间字段使用真实单调时钟时间戳，示例中的 0 仅用于说明结构。

重点计算：

1. Chunk Generation Time：音频块生成耗时。
2. Chunk Duration：音频块实际播放时长。
3. Chunk Arrival Interval：相邻音频块到达间隔。
4. Playback Gap：前一块结束与后一块开始之间的实际间隙。
5. Buffer Duration：前端剩余可播放音频时长。
6. Real-Time Factor：

RTF = 音频生成耗时 / 音频时长

额外增加：
- 每个 chunk 首尾静音时长。
- WAV 合并前后总时长差异。
- 前端播放队列长度。
- WebSocket 发送和接收队列长度。

注意区分模型生成时间与播放器播放时间，不能混用时间戳。

## 五、第四阶段：音频波形和静音分析

使用 Python 对 A、B 两组音频进行分析。

要求：
1. 绘制完整音频波形。
2. 计算短时 RMS 能量。
3. 统计连续低能量区间。
4. 检查每个 chunk 的开头和结尾。
5. 分析相邻 chunk 之间是否存在异常静音。
6. 对比 A 与 B 的静音分布。

建议同时生成：
- 音频波形图。
- RMS 能量图。
- chunk 时间轴图。
- 静音区间统计表。

静音阈值不能随意固定，需要根据录音的整体响度设定，并同时保留原始波形供人工判断。

## 六、第五阶段：排查结果与根因判断

按照以下判断矩阵分析：

| 实验结果 | 优先排查方向 |
|---|---|
| A 异常 | 模型推理、文本处理、参考音频、生成参数 |
| A 正常，B 异常 | 流式推理、chunk 拼接、上下文连续性 |
| A、B 正常，C 异常 | 文件传输、音频格式、解码、播放器 |
| A、B、C 正常，D 异常 | WebSocket、实时缓冲、播放调度 |
| A、B 都存在相同逐字停顿 | 模型配置、参考音频、文本输入及韵律条件 |

如果 A 原始输出正常，但 D 异常，不允许直接得出模型质量不足的结论。

## 七、执行约束

1. 不替换 CosyVoice3。
2. 不替换 SenseVoice。
3. 不改变现有模型架构。
4. 不擅自降低 FP16 精度。
5. 不通过增加固定静音或强行删除静音掩盖问题。
6. 不直接修改生产播放逻辑。
7. 所有测试使用独立测试脚本和独立输出目录。
8. 尽量复用现有模型实例，避免重复加载造成显存干扰。
9. 保留原始音频文件和完整诊断日志。
10. 如果发现代码问题，先提供证据和修复建议，等待确认后再修改。

### 3. 根因判断
明确指出：
- 根因所在模块
- 触发条件
- 可复现步骤
- 日志或音频证据
- 根因置信度

### 4. 修复方案
提供：
- 最小修改方案
- 推荐修改方案
- 可能的副作用
- 修改后验收标准

本次任务的最终目标是找到逐字顿挫的真实原因，而不是通过主观调整参数让声音暂时听起来好一些。
